# Что ты описываешь и как это правильно собрать

Давай разложу по частям, потому что то, что ты описал — это не «инструмент», а **платформа из 4-5 подсистем**, и главная ошибка тут — пытаться сделать «одну универсальную кнопку». Лучше собрать конструктор из понятных блоков, где каждый можно менять.

## Из чего реально состоит такая система

**1. Приём «вводных» по проекту (Intake)**
Тут ты сам предложил 4 сценария, и все они валидны. Правильно — не выбирать один, а сделать **адаптивный intake**:
- минимум: ссылка на сайт + 1-2 строки контекста;
- если LLM видит, что данных мало — задаёт **уточняющие вопросы по одному** (не анкету на 20 полей, а диалог);
- список вопросов генерится под нишу, но с «якорными» блоками, которые есть всегда (что продаём, кому, чем отличаемся, гео, размер сделки, кто ЛПР).

Сохраняй всё в структуру **Project → Brief** (JSON), потому что дальше все модули будут читать именно его.

**2. Целеполагание и сегментация (ICP builder)**
LLM из брифа собирает:
- ICP (ideal customer profile): отрасли, размер, гео, триггеры;
- анти-ICP (кого НЕ трогаем);
- 2-4 **сегмента** с гипотезами боли под каждый;
- список ролей ЛПР/инфлюенсеров.

Это критично: без явного ICP любой поиск превращается в мусор.

**3. OSINT / sourcing (поиск конкретных людей и компаний)**
Тут «просто погуглить через LLM» — плохая идея, будет галлюцинации. Нужен **слой источников**:
- веб-поиск (Serper/Brave/Google CSE) + парсинг сайтов;
- LinkedIn / Crunchbase / реестры (в РФ — ЕГРЮЛ, Rusprofile, Закупки, отраслевые каталоги);
- АПИ обогащения (email/телефон/должность) — Apollo, Hunter, Snov, или локальные;
- LLM тут — **не искатель, а нормализатор и ранжировщик**: собирает «сырые» результаты, приводит к карточке контакта, скорит по ICP.

Результат — база **Contacts + Companies** с полем `score` и `reason`.

**4. Генерация сообщений (Outreach composer)**
- шаблоны по сегментам + персонализация через LLM (не «Дорогой клиент», а «вижу, у вас недавно запустили линию X»);
- каналы: email (SMTP/ESP), Telegram (user-бот через твой аккаунт или бот), WhatsApp — по возможности;
- для каждого канала — свой формат (email длиннее, TG короче);
- **обязательный human-in-the-loop**: очередь на ревью, «отправить / отредактировать / отклонить».

**5. Отправка и ритм (Sending + Ramp-up)**
- очередь с **rate limit** (например, 5-10 писем/час на ящик первые дни);
- прогрев доменов/аккаунтов, ротация ящиков;
- отправка «от имени сотрудника» — либо через его реальный ящик (SMTP/IMAP), либо через общий с подписью (юридически и по deliverability это разные вещи, подумай);
- стоп-листы, отписки, обработка bounce.

**6. Обратная связь и обучение (Feedback loop)**
- трекинг: open / reply / click (для email — пиксель/трекинг-домен; для TG — сам факт ответа);
- классификация ответов LLM'кой (интерес / отказ / не тот адресат / автоответчик);
- **A/B по «схемам»**: сегмент × шаблон × оффер × время. Метрики: reply rate, positive reply rate, meetings booked;
- если reply rate ниже порога N на выборке M — система предлагает ревизию (переписать оффер, сменить сегмент, сменить канал).

Это, по сути, **CRM + marketing automation + OSINT-агент**, заточенные под твой кейс.

# Отлично, тогда собираем «Outreach OS» как набор API-first микросервисов

Раз ты сразу хочешь автономные сервисы (чтобы потом каждый можно было дёрнуть из других проектов), — это правильный ход. Давай зафиксирую **архитектурный каркас**, контракты между сервисами и порядок сборки. UI — потом, тонким слоем.

## Принципы (зашиваем в фундамент)

1. **API-first**: у каждого сервиса есть OpenAPI-схема, версия, аутентификация (service token + tenant header).
2. **Мульти-тенантность с первого дня**, но не «одна БД на тенанта» — а `tenant_id` в каждой таблице + RLS в Postgres. Это дёшево и не мешает потом вынести крупного клиента на отдельную БД.
3. **Асинхронность по умолчанию**: сервисы общаются событиями (NATS или Redis Streams), а синхронно — только там, где реально нужен ответ сразу (например, intake → бриф).
4. **Stateless-сервисы**, состояние только в Postgres/объектном хранилище. Любой сервис можно перезапустить/размножить.
5. **Идемпотентность**: у всех операций записи — `idempotency_key`. Это критично, когда агент будет ретраить.
6. **Единый LLM-шлюз** — не давай каждому сервису свой ключ и свою обёртку. Один сервис `llm-gateway` с учётом токенов, кэшем, ротацией промптов. DeepSeek — как провайдер по умолчанию, остальные подключаемы.
7. **Наблюдаемость с нуля**: structured logs (JSON), trace_id сквозной, метрики Prometheus, каждый вызов LLM/API — с ценой.

## Микросервисы (первая волна)

### Ядро

**1. `tenant-service`**
- CRUD по тенантам (по сути — «проект» в твоём понимании).
- Статусы: `active / paused / archived / deleted`.
- Хранит: название, ниша, бриф, ICP-конфиг, привязку ящиков/аккаунтов, лимиты.
- Даёт эндпоинты другим сервисам: «дай настройки тенанта X», «проверь квоту».
- Архив — это soft-delete с флагом, все остальные сервисы обязаны фильтровать archived по умолчанию.

**2. `llm-gateway`**
- Единая точка выхода в LLM (DeepSeek сначала, потом добавляешь OpenAI/Anthropic/локальные).
- Роутинг: задача → модель → промпт-шаблон.
- Учёт токенов по тенанту/задаче, лимиты, ретраи, кэш ответов на одинаковые запросы.
- Логирование промптов/ответов (для отладки и A/B).

**3. `brief-service` (intake)**
- Принимает вводные по проекту в любом виде: текст, ссылка, голосовое (транскрипт через LLM), ответы на вопросы.
- Через `llm-gateway` задаёт уточняющие вопросы, если данных мало.
- На выходе — **структурированный Brief** (JSON-схема фиксированная). Это ключевой контракт: все остальные сервисы читают только Brief, а не сырой ввод.
- Схема брифа — версионируемая, чтобы можно было эволюционировать.

### Аналитика и таргетинг

**4. `icp-service`**
- Из Brief строит ICP + анти-ICP + 2-4 сегмента с гипотезами боли + роли ЛПР.
- Отдаёт всё в машиночитаемом виде: критерии сегмента (отрасль, размер, гео, триггеры) + скоринг-веса.
- Это тоже версионируемый артефакт — потом сравниваешь результаты outreach по разным версиям ICP.

**5. `sourcing-service` (OSINT)**
- Вход: ICP + сегмент + гео.
- Выход: список кандидатов (Company + Contact) со скорингом и `reason`.

  - парсер сайтов (cheerio/playwright);
  - реестры РФ (ЕГРЮЛ/Rusprofile/Закупки/отраслевые каталоги) — через свои обёртки;
  - зарубежные (Crunchbase, LinkedIn public) — на этапе глобал;
  - обогащение email/телефон — Hunter/Snov/Apollo, плюс собственные эвристики.
- LLM тут — **нормализатор и скорер**, не искатель. Обязательно сохраняй `source_url` и `evidence` для каждого поля.
- Отдаёт кандидатов в `contact-store`.

**6. `contact-store`**
- Единая БД компаний и контактов (тенант-скоупная).
- Дедупликация по домену/email/телефону (fingerprint).
- История: кто уже получал письма, от кого, какая реакция.
- Глобальные стоп-листы (по тенанту и по всей системе).

### Сообщения

**7. `composer-service`**
- Вход: Contact + Company + Brief + ICP + канал (email/tg/whatsapp).
- Выход: черновик сообщения + список «фактов-оснований» (что именно взято из источника).
- Обязательная валидация: каждое утверждение в письме должно иметь `evidence_url` или быть помечено как «гипотеза».
- Версии шаблонов, привязка к A/B-экспериментам.

**8. `review-queue`**
- Очередь на human-in-the-loop.
- Может быть как сервис, так и просто таблица + API. Для агентной разработки — пусть будет сервис с API (approve/reject/edit).
- Статусы сообщения: `draft → pending_review → approved → queued → sent → bounced → replied → closed`.

### Отправка

**9. `sender-email`**
- Отдельный сервис (потому что сложный и критичный).
- Подключение ящиков: SMTP/IMAP (или API провайдера, если есть).
- Ротация ящиков, per-mailbox rate limit, ramp-up (прогрев), throttling.
- Обработка bounce/complaint, отписки, reply-detection.
- Логирование каждого шага (для deliverability-анализа).
- SPF/DKIM/DMARC — настраивается на уровне домена, но сервис должен валидировать и алертить.

**10. `sender-messenger`** (позже)
- Telegram (user-аккаунт через MTProto + бот), WhatsApp (Business API).

# Мини-ликбез по NATS (5 минут)

NATS — это брокер сообщений. Модель простая:

**Core NATS** — pub/sub без гарантий. Отправил — забыл. Если подписчик офлайн, сообщение потеряется.

**JetStream** — надстройка над core NATS, даёт:
- **Streams** — это «топики с persistence». Ты создаёшь стрим `briefs`, говоришь «слушай subject `brief.created.>`», и все сообщения сохраняются.
- **Consumers** — подписки на стрим. Бывают **push** (NATS сам шлёт) и **pull** (подписчик сам тянет). Для наших сервисов — pull, потому что контроль лучше.
- **Ack** — подписчик подтверждает обработку. Не подтвердил — NATS переотправит (at-least-once).
- **Deliver policy** — с какого места начинать: `all` (всё с начала), `last` (последнее), `new` (только новые).
- **KV Store** — key-value поверх JetStream. Можно использовать для идемпотентности, но у нас есть Redis, так что не обязательно.
- **Object Store** — файлы поверх JetStream. Альтернатива MinIO для мелких файлов.

**Ключевые понятия в нашем контексте:**
- Subject — иерархическая строка, например `brief.created.<tenant_id>`. Можно подписаться на `brief.created.*` или `brief.>`.
- Stream — контейнер, который хранит сообщения по определённым subject'ам с retention policy (например, 30 дней или 1 ГБ).
- Consumer — конкретная подписка с именем (durable). Если сервис упал и перезапустился — consumer продолжит с того же места.

**Аналогия с Redis:** представь, что Redis Streams — это один стрим на всё, а NATS JetStream — это много независимых стримов с гибкой маршрутизацией, retention policy на каждый и нормальным ack-механизмом. Плюс NATS умеет кластеризацию из коробки, если вырастешь.

**Почему NATS, а не Redis Streams у нас:**
1. Subjects позволяют гибко роутить без парсинга payload (`brief.created.*` vs `brief.updated.*`).
2. JetStream consumer'ы — durable по умолчанию, с явным ack и retry policy.
3. Отдельные retention на разные типы событий (логи LLM храним 7 дней, бизнес-события — год).
4. Меньше шансов случайно сломать шину, если кто-то сделает `FLUSHDB` в Redis.

**Что тебе нужно знать для работы:** subject naming convention, создание стрима и consumer'а, ack/nack. Всё. Остальное — детали.

Мы будем использовать библиотеку **`nats-py`** (async, официальная).

## По Traefik и Caddy: три варианта, один правильный

Ситуация: на dev-сервере уже стоит Caddy, слушает 80/443. Хочешь поставить Traefik для твоих сервисов.

### Вариант 1 (плохой): Traefik на других портах

Traefik слушает 8080/8443, Caddy проксирует на него по домену. **Проблемы:**
- Двойное TLS-терминирование (Caddy расшифровывает → Traefik заново шифрует или наоборот).
- Сложно с автоматическими сертификатами: у Traefik свой ACME, у Caddy свой. Могут конфликтовать за порты/челленджи.
- Если Traefik за Caddy, теряется весь смысл Traefik (динамическое обнаружение контейнеров) — Caddy всё равно должен знать, куда проксировать.

### Вариант 2 (рабочий, но костыльный): Caddy front, Traefik behind

Caddy держит 80/443, проксирует на Traefik (например, `localhost:7443`) по определённым доменам [citation:3]. Внутри Caddyfile:
```caddy
*.outreach.aitler.ru {
    reverse_proxy https://traefik:7443 {
        transport http {
            tls_insecure_skip_verify
        }
    }
}
```
**Минусы:**
- Двойная расшифровка/шифровка — Caddy расшифровал, потом Traefik внутри [citation:3].
- Если нужны WebSocket/HTTP3 — всё ломается.
- Caddy и Traefik оба хотят управлять сертификатами, могут быть конфликты [citation:14][citation:20].

### Вариант 3 (рекомендую): **Caddy — единственный edge-прокси, Traefik не ставим**

Почему:

1. **Caddy уже работает и делает то же самое.** Автоматический HTTPS, ACME, reverse proxy. Ставить Traefik поверх — это решение без проблемы.

2. **Traefik хорош для Kubernetes и динамических окружений** [citation:8]. Для docker-compose на VPS с 5-15 сервисами Caddy справляется не хуже, а конфиг проще.

3. **Caddy + Docker labels** (через `caddy-docker-proxy`) [citation:15] даёт тот же эффект, что Traefik: контейнеры сами регистрируются, Caddy автоматически проксирует.

**Что делаем:**
- Оставляем **Caddy** как edge-прокси на dev.
- Для наших сервисов используем **caddy-docker-proxy**: каждый контейнер в docker-compose получает labels, Caddy читает их и создаёт маршруты автоматически.
- Пример для сервиса:
```yaml
services:
  tenant-service:
    image: outreach/tenant-service:dev
    labels:
      caddy: "tenant.dev.aitler.ru"
      caddy.reverse_proxy: "{{upstreams 8000}}"
```
- Caddy сам получит Let's Encrypt (или self-signed для dev) и направит трафик на контейнер.

**Для stage/prod** — та же схема. Если Caddy уже используется, не дублируем reverse-proxy.

**Единственный сценарий, где Traefik оправдан:** если ты планируешь мигрировать на k8s в ближайшие месяцы. Тогда Traefik с его CRD и IngressRoute будет нативнее. Но для docker-compose — нет.

# Решения по NATS и финализация Спринта 0

## По NATS: ставим на том же VPS, вот почему

**Бест-практика для нашего масштаба:** NATS JetStream в том же docker-compose, что и остальная инфра. Причины:

1. **NATS — это не тяжёлый брокер.** Один бинарник ~20 МБ, RAM 50-100 МБ на нашу нагрузку. В отличие от Kafka (JVM, гигабайты RAM) он лёгкий.
2. **Сетевые задержки.** На одном хосте — микросекунды. Отдельный VPS добавит миллисекунды и точку отказа.
3. **Persistence.** JetStream пишет на диск в volume. Если контейнер упадёт — при рестарте поднимется и продолжит с того же места.
4. **Кластеризация — потом.** Если вырастешь, NATS умеет кластеризоваться в 3 ноды. Но это не задача Спринта 0.

**Что важно настроить сразу (иначе потом больно):**

- **JetStream с file storage** (не memory). Memory — только для эфемерных событий.
- **Отдельный volume** для данных NATS, чтобы не терялся при пересборке.
- **Max age на стримы** — например, бизнес-события храним 90 дней, логи LLM — 7 дней. Иначе диск забьётся.
- **Max bytes на стримы** — жёсткий лимит, чтобы один разбушевавшийся сервис не забил диск.
- **Auth**: username/password или token (не «без аутентификации», даже на dev).
- **Monitoring port 8222** — оттуда Prometheus будет скребсти метрики.

**Стримы, которые создаём в Спринте 0:**

| Stream | Subjects | Retention | Max Age |
|---|---|---|---|
| `TENANTS` | `tenant.>` | Limits | 365d |
| `BRIEFS` | `brief.>` | Limits | 365d |
| `LLM_CALLS` | `llm.>` | Limits | 7d |
| `SYSTEM` | `system.>` | WorkQueue | 7d |

WorkQueue для `SYSTEM` — события, которые обрабатываются ровно один раз и потом удаляются (например, задачи на отправку). Limits для остальных — обычное хранилище с лимитами по возрасту/размеру.

**Naming convention для subjects:**
```
<domain>.<action>.<tenant_id>
```
Примеры:
- `tenant.created.<tenant_id>`
- `tenant.archived.<tenant_id>`
- `brief.created.<tenant_id>`
- `llm.called.<tenant_id>`

Подписка на все события тенанта: `tenant.>.<tenant_id>` или просто `tenant.>` если слушаем всё.

**Что тебе нужно знать для эксплуатации:**
- `nats stream ls` — список стримов (через `nats` CLI в контейнере).
- `nats stream info BRIEFS` — сколько сообщений, размер.
- `nats consumer ls BRIEFS` — какие подписчики.
- Если что-то зависло: `nats consumer info BRIEFS <name>` показывает pending/ack.

CLI `nats` можно запускать через `docker exec -it nats nats ...` — добавим алиас в runbook.

Я перепроверил каждую схему на: (1) полноту покрытия твоих сценариев, (2) версионируемость, (3) отсутствие циклических зависимостей, (4) готовность к мульти-тенантности, (5) совместимость с NATS-событиями, (6) пригодность для A/B-анализа.

---

## 0. Общие принципы

### 0.1. Версионирование схем

Каждый контракт имеет поле `schema_version` в формате `major.minor`. Правила:
- **major** инкрементится при breaking changes (удаление поля, смена типа, изменение семантики).
- **minor** инкрементится при добавлении опциональных полей.
- Потребитель обязан игнорировать неизвестные поля (forward compatibility).
- Сервис, читающий контракт, проверяет `schema_version.major` и падает с ошибкой при несовпадении.

Текущие версии: `brief/1.0`, `icp/1.0`, `contact/1.0`, `company/1.0`, `message/1.0`, `event/1.0`.

### 0.2. Общие типы

Все контракты используют общие примитивы:

```
TenantId        = UUID v7 (time-ordered, для сортировки по времени создания)
EntityId        = UUID v7
Timestamp       = RFC3339 UTC, миллисекундная точность, всегда с 'Z'
LanguageCode    = BCP-47 (например, "ru", "en", "ru-RU")
CountryCode     = ISO 3166-1 alpha-2 (например, "RU", "KZ")
CurrencyCode    = ISO 4217 (например, "RUB", "USD")
Url             = абсолютный URL, http/https
Email           = RFC 5322, нормализованный в lowercase
Phone           = E.164 (например, "+79001234567")
```

**Почему UUID v7:** time-ordered, хорошо для индексов в Postgres, сортируется по времени создания. Генерируется библиотекой `uuid6` на Python.

### 0.3. Общие поля всех сущностей

Каждая сущность (Brief, ICP, Contact, Company, Message) имеет:

```json
{
  "id": "EntityId",
  "tenant_id": "TenantId",
  "schema_version": "1.0",
  "created_at": "Timestamp",
  "updated_at": "Timestamp",
  "created_by": "string",        // user_id или "system" или "agent:<name>"
  "trace_id": "string",          // сквозной trace для отладки
  "metadata": {}                 // свободный словарь, не индексируется
}
```

Поле `metadata` — для экспериментальных данных, не влияет на логику. Потом можно повысить до полноценного поля.

### 0.4. Evidence-принцип

**Любое утверждение о факте** (компания существует, у неё есть сайт, у человека должность CTO) должно иметь `evidence`:

```json
{
  "value": "CTO",
  "confidence": 0.85,
  "evidence": [
    {
      "source_url": "https://example.com/team",
      "source_type": "website",
      "extracted_at": "Timestamp",
      "snippet": "Иван Петров, CTO с 2021 года"
    }
  ]
}
```

`confidence` — 0.0–1.0. Если ниже 0.5 — поле считается ненадёжным, composer не должен на него опираться. `evidence` может быть пустым (для фактов, введённых человеком вручную) — тогда `confidence = 1.0` и `source_type = "manual"`.

Этот принцип применяется в Contact, Company, ICP. В Brief — частично (там вводные от человека, evidence не нужен, но есть `source` для ссылок/транскриптов).

### 0.5. Мульти-тенантность

Правило: **любой объект принадлежит ровно одному тенанту**. Кросс-тенантные данные — только справочники (страны, отрасли) и глобальные стоп-листы. При передаче между сервисами `tenant_id` идёт всегда в headers (HTTP: `X-Tenant-ID`; NATS: header `tenant_id`), а в payload дублируется для self-describing событий.

### 0.6. NATS subjects (полная карта на Спринты 0–5)

```
<domain>.<action>.<tenant_id>

tenant.created.<tid>
tenant.updated.<tid>
tenant.archived.<tid>
tenant.restored.<tid>

brief.created.<tid>
brief.updated.<tid>
brief.questions_asked.<tid>
brief.completed.<tid>

icp.generated.<tid>
icp.revised.<tid>

contacts.search_started.<tid>
contacts.found.<tid>
contacts.enriched.<tid>

message.drafted.<tid>
message.approved.<tid>
message.rejected.<tid>
message.queued.<tid>
message.sent.<tid>
message.bounced.<tid>

reply.received.<tid>
reply.classified.<tid>

```

## 1. Brief v1

**Назначение:** структурированное описание проекта/ниши, из которого всё строится. Источник — intake (текст, ссылка, ответы на вопросы, транскрипт голосового).

### 1.1. Схема

```json
{
  "id": "EntityId",
  "tenant_id": "TenantId",
  "schema_version": "1.0",
  "created_at": "Timestamp",
  "updated_at": "Timestamp",
  "created_by": "string",
  "trace_id": "string",
  "metadata": {},

  "status": "draft | in_progress | complete | abandoned",

  "raw_input": {
    "text": "string | null",
    "urls": ["Url"],
    "attachments": [
      {
        "id": "EntityId",
        "filename": "string",
        "mime_type": "string",
        "size_bytes": 12345,
        "storage_url": "string"
      }
    ],
    "transcript": "string | null",
    "submitted_at": "Timestamp"
  },

  "qa_history": [
    {
      "question": "string",
      "answer": "string",
      "asked_at": "Timestamp",
      "answered_at": "Timestamp",
      "generated_by": "llm:<model> | manual",
      "question_template_id": "string | null"
    }
  ],

  "identity": {
    "project_name": "string",
    "company_name": "string | null",
    "company_url": "Url | null",
    "one_liner": "string | null",
    "industry": "string | null",
    "sub_industry": "string | null",
    "language": "LanguageCode",
    "geo_primary": ["CountryCode"],
    "geo_secondary": ["CountryCode"]
  },

  "offering": {
    "what_we_sell": "string",
    "categories": ["string"],
    "differentiators": ["string"],
    "proof_points": ["string"],
    "price_range": {
      "min": "number | null",
      "max": "number | null",
      "currency": "CurrencyCode | null",
      "model": "fixed | subscription | usage | custom | unknown"
    },
    "sales_cycle_days_estimate": "integer | null"
  },

  "targeting_hints": {
    "known_competitors": ["string"],
    "known_customers_examples": ["string"],
    "must_have_criteria": ["string"],
    "must_not_have_criteria": ["string"],
    "geography_notes": "string | null",
    "company_size_hint": "smb | mid | enterprise | any | null",
    "role_hints": ["string"]
  },

  "outreach_goals": {
    "primary_goal": "lead_gen | partnership | hiring | pr | research | other",
    "goal_description": "string | null",
    "target_meetings_per_month": "integer | null",
    "tone_of_voice": "formal | casual | technical | friendly | neutral",
    "forbidden_topics": ["string"],
    "required_mentions": ["string"]
  },

  "missing_info": [
    {
      "field": "string",
      "why_needed": "string",
      "priority": "high | medium | low"
    }
  ],

  "completeness_score": 0.0
}
```

### 1.2. Правила

- `completeness_score` (0.0–1.0) вычисляется `brief-service` по формуле: взвешенная сумма заполненности ключевых полей. Веса: identity 0.25, offering 0.30, targeting_hints 0.20, outreach_goals 0.25.
- Если `completeness_score < 0.7` — `brief-service` генерирует вопросы и добавляет в `qa_history` (записывает вопрос без ответа, `answered_at: null`).
- Статус `complete` ставится либо автоматически при `completeness_score >= 0.85`, либо вручную пользователем.
- `missing_info` заполняется LLM: какие поля критичны, но не заполнены.

### 1.3. Пример

```json
{
  "id": "0190f3a2-...",
  "tenant_id": "0190f3a1-...",
  "schema_version": "1.0",
  "status": "in_progress",
  "raw_input": {
    "text": "Знакомый делает гидроборты, хочет выйти на дистрибьюторов в РФ",
    "urls": ["https://gidrobort-example.ru"],
    "submitted_at": "2026-09-30T10:00:00Z"
  },
  "identity": {
    "project_name": "Гидроборты — дистрибьюторы РФ",
    "company_url": "https://gidrobort-example.ru",
    "industry": "Промышленное производство",
    "sub_industry": "Подъёмно-транспортное оборудование",
    "language": "ru",
    "geo_primary": ["RU"]
  },
  "offering": {
    "what_we_sell": "Гидроборты для грузового транспорта",
    "categories": ["гидроборты", "подъёмники"],
    "differentiators": ["Собственное производство", "Гарантия 3 года"],
    "price_range": {"model": "custom", "currency": "RUB"}
  },

    {"field": "targeting_hints.known_customers_examples", "why_needed": "Поможет найти похожих клиентов", "priority": "high"},
    {"field": "offering.price_range.min", "why_needed": "Влияет на сегментацию по размеру клиента", "priority": "medium"}
  ]
}
```

## 2. ICP v1

**Назначение:** формализованный профиль идеального клиента/партнёра, разбитый на сегменты. Вход для sourcing.

### 2.1. Схема

```json
{
  "id": "EntityId",
  "tenant_id": "TenantId",
  "brief_id": "EntityId",
  "schema_version": "1.0",
  "created_at": "Timestamp",
  "updated_at": "Timestamp",
  "created_by": "string",
  "trace_id": "string",
  "metadata": {},

  "version": 1,

  "anti_icp": {
    "description": "string",
    "exclude_industries": ["string"],
    "exclude_company_sizes": ["smb | mid | enterprise"],
    "exclude_geos": ["CountryCode"],
    "exclude_keywords": ["string"]
  },

  "segments": [
    {
      "id": "EntityId",
      "name": "string",
      "description": "string",
      "priority": "high | medium | low",
      "estimated_size": "integer | null",

      "firmographic": {
        "industries": ["string"],
        "sub_industries": ["string"],
        "company_sizes": ["smb | mid | enterprise"],
        "employee_count_min": "integer | null",
        "employee_count_max": "integer | null",
        "revenue_range": {
          "min": "number | null",
          "max": "number | null",
          "currency": "CurrencyCode | null"
        },
        "geos": ["CountryCode"],
        "company_types": ["manufacturer | distributor | retailer | service | agency | saas | other"]
      },

      "technographic": {
        "uses_technologies": ["string"],
        "does_not_use_technologies": ["string"]
      },

      "pain_hypotheses": [
        {
          "pain": "string",
          "why_relevant": "string",
          "how_we_solve": "string",
          "confidence": 0.0
        }
      ],

      "trigger_events": [
        {
          "trigger": "string",
          "detection_hint": "string",
          "weight": 0.0
        }
      ],

      "roles_to_contact": [
        {
          "role_title": "string",
          "role_category": "decision_maker | influencer | gatekeeper | champion | unknown",
          "priority": "high | medium | low",
          "why": "string"
        }
      ],

      "scoring_weights": {
        "industry_match": 0.25,
        "size_match": 0.15,
        "geo_match": 0.10,
        "pain_match": 0.20,
        "trigger_match": 0.20,
        "role_match": 0.10
      },

      "estimated_reply_rate": "number | null",
      "notes": "string | null"
    }
  ],

  "generated_by": "llm:<model> | manual",
  "llm_confidence": 0.0
}
```

### 2.2. Правила

- Веса в `scoring_weights` для каждого сегмента должны суммироваться в 1.0 (валидатор Pydantic).
- `version` инкрементится при каждом ре-генерейте ICP для того же brief. Старые версии сохраняются — нужны для A/B-анализа метрик outreach.
- `estimated_reply_rate` — прогноз LLM, потом сравнивается с реальностью, ошибка идёт в аналитику.
- Если `llm_confidence < 0.6` — `icp-service` помечает ICP как «требует ревью человеком» (флаг в metadata).

## 3. Company v1

**Назначение:** карточка компании-кандидата.

### 3.1. Схема

```json
{
  "id": "EntityId",
  "tenant_id": "TenantId",
  "schema_version": "1.0",
  "created_at": "Timestamp",
  "updated_at": "Timestamp",
  "created_by": "string",
  "trace_id": "string",
  "metadata": {},

  "fingerprint": "string",   // sha256(normalized_domain || normalized_name)
  "status": "candidate | contacted | replied | qualified | disqualified | archived",

  "name": {"value": "string", "confidence": 1.0, "evidence": []},
  "legal_name": {"value": "string | null", "confidence": 0.0, "evidence": []},
  "domain": {"value": "string | null", "confidence": 0.0, "evidence": []},
  "website": {"value": "Url | null", "confidence": 0.0, "evidence": []},

  "industry": {"value": "string | null", "confidence": 0.0, "evidence": []},
  "sub_industry": {"value": "string | null", "confidence": 0.0, "evidence": []},

  "size_estimate": {
    "employee_count": {"value": "integer | null", "confidence": 0.0, "evidence": []},
    "employee_range": "smb | mid | enterprise | unknown",
    "revenue_estimate": {"value": "number | null", "confidence": 0.0, "evidence": []},
    "revenue_currency": "CurrencyCode | null"
  },

  "locations": [
    {
      "country": {"value": "CountryCode | null", "confidence": 0.0, "evidence": []},
      "city": {"value": "string | null", "confidence": 0.0, "evidence": []},
      "address": {"value": "string | null", "confidence": 0.0, "evidence": []},
      "is_hq": true
    }
  ],

  "registry_ids": {
    "ru_inn": "string | null",
    "ru_ogrn": "string | null",
    "other": {"key": "value"}
  },

  "social_profiles": {
    "linkedin": "Url | null",
    "telegram": "string | null",
    "vk": "Url | null",

  "tech_stack": [

    {
      "type": "hiring | funding | launch | expansion | award | news | other",
      "summary": "string",
      "detected_at": "Timestamp",
      "source_url": "Url",

    }
  ],

  "match": {
    "segment_id": "EntityId | null",
    "icp_version": 1,
    "score": 0.0,
    "score_breakdown": {
      "industry_match": 0.0,

    "total_contacts": 0,
    "total_messages": 0,
    "last_contacted_at": "Timestamp | null"

  "tags": ["string"],
  "notes": "string | null"
}
```

### 3.2. Правила

- `fingerprint` — ключ дедупликации. Вычисляется как sha256 от нормализованного домена (без www, lowercase) или, если домена нет, от нормализованного названия (lowercase, без ООО/LLC и т.п.).
- Все поля, кроме `name` и `fingerprint`, опциональны с confidence 0.0. Это позволяет создавать «частичные» карточки по мере обогащения.
- `match.score` пересчитывается при каждом новом сигнале или обогащении.
- `signals` — самый важный блок для персонализации писем. Composer берёт оттуда «крючок».

- Если `status = unsubscribed` — контакт никогда не попадает в новые очереди, даже если попал в sourcing.

## 10. Правила совместимости

1. **Никаких breaking changes без major-инкремента.** Если нужно удалить поле — деprecate на minor, удаление через major.
2. **Потребитель игнорирует неизвестные поля** (Pydantic `model_config = ConfigDict(extra="ignore")`).
3. **Producer всегда пишет `schema_version`** — иначе событие отклоняется брокером (валидатор в nats-client).
4. **Сервис, читающий событие, проверяет `schema_version.major`** — при несовпадении nack и алерт.
5. **Backward compatibility на 1 major-версию вперёд** — если producer 1.0, consumer 1.x — работает. Если producer 2.0, consumer 1.x — не работает, требуется миграция.

## 11. Схема БД (таблицы, которые соответствуют контрактам)

На уровне Postgres каждое поле верхнего уровня — колонка, вложенные структуры — JSONB. Пример:

```sql
CREATE TABLE briefs (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  schema_version TEXT NOT NULL,
  status TEXT NOT NULL,
  completeness_score NUMERIC(3,2),
  raw_input JSONB,
  qa_history JSONB,
  identity JSONB,
  offering JSONB,
  targeting_hints JSONB,
  outreach_goals JSONB,
  missing_info JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by TEXT,
  trace_id TEXT,
  metadata JSONB DEFAULT '{}'::jsonb
);

CREATE INDEX ON briefs (tenant_id, status);
CREATE INDEX ON briefs (tenant_id, created_at DESC);

ALTER TABLE briefs ENABLE ROW LEVEL SECURITY;
CREATE POLICY briefs_tenant_isolation ON briefs
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

Аналогично для остальных. Вложенные структуры — JSONB, потому что они либо читаются целиком, либо не читаются. Индексировать отдельные поля внутри будем через GIN-индексы по мере необходимости.

**Исключение:** `contacts.emails` и `contacts.phones` — выносим в отдельные таблицы `contact_emails`, `contact_phones` для быстрого поиска по email/phone (дедупликация, проверка стоп-листов). Аналогично `messages` — выносим `message_status_history` для аудита.

1. **Postgres/NATS/Redis/MinIO порты только на `127.0.0.1`** — не торчат наружу. Доступ через SSH-туннель для отладки.
2. **Caddy слушает 80/443 на всех интерфейсах** — это единственный edge.
3. **`CADDY_INGRESS_NETWORKS: outreach-net`** — Caddy видит только контейнеры этой сети.
4. **Labels на сервисах** — Caddy автоматически создаёт маршруты `tenant.dev.aitler.ru → tenant-service:8000`.
5. **Healthchecks везде** — `depends_on` с `condition: service_healthy` гарантирует порядок.
6. **Логи с ротацией** — не забиваем диск.
7. **Volumes с явными именами** — не теряются при пересоздании проекта.
8. **`env_file: ../.env.dev`** — секреты вне репы.

**Важно про Caddy и уже существующий Caddy на dev:**

Если у тебя уже стоит Caddy на dev-сервере (системный или в другом compose), то **этот compose не должен его замещать**. Варианты:

- **(A) Заменить существующий Caddy на этот** — если он не занят другими проектами. Останавливаешь старый, поднимаешь новый, переносишь конфиги в labels.
- **(B) Оставить старый как edge, а этот — убрать** из compose, и в старом Caddyfile добавить reverse_proxy на наши сервисы вручную. Менее удобно, но не ломает существующее.
- **(C) Использовать caddy-docker-proxy как плагин к существующему Caddy** — пересобрать существующий Caddy с плагином, подключить к docker.sock, и он сам увидит labels наших контейнеров. Это самый аккуратный вариант, если старый Caddy уже обслуживает другие проекты.

**Рекомендую (C).** Тогда из нашего compose блок `caddy` убирается, а в существующем Caddy добавляется плагин и `CADDY_INGRESS_NETWORKS` указывает на все сети, включая `outreach-net`.

Если выберешь (A) — оставляем как есть в compose.

```conf
          allow: [">"]
        }
      }
    }
  ]

}

# JetStream
jetstream {
  store_dir: "/data/jetstream"

  max_file_store: 10GB

```

**Проблема:** NATS не читает env-переменные напрямую для пароля в конфиге. Есть три решения:

1. **`nats-server --user $NATS_USER --pass $NATS_PASSWORD`** в command — переопределяет конфиг. Именно так сделано в compose выше (в `command`). Тогда в конфиге блок `authorization` **не нужен** — оставляем только лимиты и JetStream.
2. Шаблонизация конфига через entrypoint-скрипт.
3. Vault/секреты.

**Выбираем (1):** конфиг без `authorization`, а user/pass передаём через command. Вот исправленный `nats-server.conf`:

```conf
server_name: "outreach-nats-dev"
port: 4222
http: 8222

debug: false
trace: false
logtime: true
log_file: "/data/nats.log"

max_payload: 4MB
max_pending: 64MB
max_connections: 1000
write_deadline: "10s"

jetstream {
  store_dir: "/data/jetstream"
  max_memory_store: 256MB
  max_file_store: 10GB
}
```

А в compose `command` будет:

```yaml
command:
  - "--config=/etc/nats/nats-server.conf"
  - "--user=${NATS_USER}"
  - "--pass=${NATS_PASSWORD}"
```

**Внимание:** `${NATS_USER}` в `command` compose подставит из `.env.dev` **на хосте** до запуска контейнера. Это работает, но пароль будет виден в `docker inspect`. На dev — приемлемо. На prod — использовать `docker secret` или передавать через env внутри контейнера и entrypoint-скрипт.

Для prod-версии я в следующем документе (runbook) распишу правильную передачу секретов.

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

CREATE EXTENSION IF NOT EXISTS "pg_trgm";      -- для fuzzy-поиска по названиям

DO $$
BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'outreach_app') THEN
    CREATE ROLE outreach_app WITH LOGIN PASSWORD 'REPLACE_VIA_ENV';
  END IF;
END
$$;

-- Даём права на схему public
GRANT CONNECT ON DATABASE outreach TO outreach_app;
GRANT USAGE ON SCHEMA public TO outreach_app;
GRANT CREATE ON SCHEMA public TO outreach_app;

-- По умолчанию для будущих таблиц
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO outreach_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT USAGE, SELECT ON SEQUENCES TO outreach_app;

-- Отдельная схема для аудита (будет использоваться позже)
CREATE SCHEMA IF NOT EXISTS audit;
GRANT USAGE ON SCHEMA audit TO outreach_app;
```

**Про пароль `outreach_app`:** в SQL-файле его не подставить из env. На dev — смириться, что пароль в файле (файл в gitignored-папке или зашифрован SOPS). На prod — entrypoint-скрипт или init-контейнер, который подставит.

**Альтернатива для dev:** использовать одного пользователя `outreach` (суперюзер) для всего. Проще, но менее безопасно. **Не рекомендую**, потому что потом сложно переучиться.

```bash
#!/usr/bin/env bash
# ============================================================
# Outreach OS — bootstrap dev environment from scratch
# ============================================================
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
ROOT_DIR="$(cd "${SCRIPT_DIR}/.." && pwd)"

RED='\033[0;31m'; GREEN='\033[0;32m'; YELLOW='\033[1;33m'; NC='\033[0m'
log()  { echo -e "${GREEN}[bootstrap]${NC} $*"; }
warn() { echo -e "${YELLOW}[bootstrap]${NC} $*"; }
```

## 18. `Dockerfile` (шаблон для сервиса, multi-stage с uv)

```dockerfile
# syntax=docker/dockerfile:1.7

# ============================================================
# Stage 1: builder — ставим uv и зависимости
# ============================================================
FROM python:3.12-slim-bookworm AS builder

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_COMPILE_BYTECODE=1 \
    UV_PYTHON_DOWNLOADS=never

# uv
COPY --from=ghcr.io/astral-sh/uv:0.5.2 /uv /uvx /bin/

WORKDIR /app

# Копируем манифесты workspace
COPY pyproject.toml uv.lock ./
COPY libs/ ./libs/
COPY services/tenant-service/ ./services/tenant-service/

# Устанавливаем зависимости только для нужного сервиса
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync \
      --frozen \
      --no-dev \
      --package tenant-service \
      --no-editable

# ============================================================
# Stage 2: runtime — минимальный образ
# ============================================================
FROM python:3.12-slim-bookworm AS runtime

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PATH="/app/.venv/bin:$PATH" \
    PYTHONPATH="/app/services/tenant-service/src:/app/libs"

RUN apt-get update && apt-get install -y --no-install-recommends \
      curl \
    && rm -rf /var/lib/apt/lists/*

# Непривилегированный пользователь
RUN groupadd --system --gid 1000 app && \
    useradd --system --uid 1000 --gid app --create-home app

WORKDIR /app

# Копируем venv и код
COPY --from=builder --chown=app:app /app/.venv /app/.venv
COPY --from=builder --chown=app:app /app/libs /app/libs
COPY --from=builder --chown=app:app /app/services/tenant-service /app/services/tenant-service

USER app

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \
  CMD curl -fsS http://localhost:8000/healthz || exit 1

# Запуск через uvicorn
CMD ["uvicorn", "tenant_service.main:app", "--host", "0.0.0.0", "--port", "8000", "--proxy-headers", "--forwarded-allow-ips", "*"]
```

**Ключевое:**
- **Multi-stage** — builder с uv и dev-зависимостями, runtime только с venv.
- **`--no-editable`** — зависимости устанавливаются как настоящие пакеты, не симлинки, чтобы работало в runtime-образе.
- **`--frozen`** — использует точные версии из `uv.lock`.
- **`--package tenant-service`** — ставит только то, что нужно этому сервису.
- **`--mount=type=cache`** — кэш uv между сборками (нужен BuildKit, в docker compose он по умолчанию).
- **Непривилегированный пользователь** — безопасность.
- **PYTHONPATH** — чтобы импорты `common`, `contracts` работали.

**Важно:** для каждого сервиса нужно поменять `--package <name>` и последний `CMD`.

```python
class EntityBase(BaseModel):
    """Базовая модель для всех сущностей."""

    model_config = ConfigDict(
        extra="ignore",  # forward compatibility
        frozen=False,
        validate_assignment=True,
        str_strip_whitespace=True,
        ser_json_timedelta="float",
    )

    id: UUID = Field(default_factory=uuid7)
    tenant_id: UUID

    created_at: datetime
    updated_at: datetime
    created_by: str = "system"
    trace_id: str = ""
    metadata: dict[str, Any] = Field(default_factory=dict)


class Evidence(BaseModel):
    """Доказательство факта."""

    model_config = ConfigDict(extra="ignore")

    source_url: str | None = None
    source_type: str  # "website" | "registry" | "linkedin" | "manual" | ...
    extracted_at: datetime
    snippet: str | None = None


class Fact(BaseModel, Generic[T]):
    """Значение с уверенностью и доказательствами."""

    model_config = ConfigDict(extra="ignore")

    value: T | None
    confidence: float = Field(ge=0.0, le=1.0)
    evidence: list[Evidence] = Field(default_factory=list)


class EventEnvelope(BaseModel, Generic[T]):
    """Обёртка для всех NATS-событий."""

    model_config = ConfigDict(extra="ignore")

    event_id: UUID = Field(default_factory=uuid7)
    event_type: str
    schema_version: str = "1.0"
    occurred_at: datetime
```

### `session.py`

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from sqlalchemy.ext.asyncio import (
    AsyncEngine,
    AsyncSession,
    async_sessionmaker,
    create_async_engine,
)

from db.rls import set_tenant_context


_engine: AsyncEngine | None = None
_session_factory: async_sessionmaker[AsyncSession] | None = None


def init_engine(database_url: str, *, echo: bool = False) -> AsyncEngine:
    global _engine, _session_factory
    _engine = create_async_engine(
        database_url,
        echo=echo,
        pool_size=10,
        max_overflow=20,
        pool_pre_ping=True,
        pool_recycle=3600,
    )
    _session_factory = async_sessionmaker(
        _engine,
        expire_on_commit=False,
        class_=AsyncSession,
    )
    return _engine


def get_engine() -> AsyncEngine:
    if _engine is None:
        raise RuntimeError("Engine not initialized. Call init_engine() first.")
    return _engine


@asynccontextmanager
async def session_scope(*, tenant_id=None) -> AsyncIterator[AsyncSession]:
    """Транзакционный scope с автоматическим SET LOCAL app.tenant_id."""
    if _session_factory is None:
        raise RuntimeError("Session factory not initialized.")
    async with _session_factory() as session:
        async with session.begin():
            if tenant_id is not None:
                await set_tenant_context(session, tenant_id)
            yield session
```

### `client.py`

```python
import asyncio
import logging
from contextlib import asynccontextmanager
from collections.abc import AsyncIterator

import nats
from nats.aio.client import Client as NATSClient
from nats.js import JetStreamContext

from nats_client.streams import STREAMS


logger = logging.getLogger(__name__)


class NATSConnection:
    """Управляет подключением к NATS и JetStream."""

    def __init__(self, url: str, *, name: str = "outreach-service") -> None:
        self._url = url
        self._name = name
        self._nc: NATSClient | None = None
        self._js: JetStreamContext | None = None
        self._lock = asyncio.Lock()

    async def connect(self) -> None:
        async with self._lock:
            if self._nc is not None and not self._nc.is_closed:
                return
            self._nc = await nats.connect(
                self._url,
                name=self._name,
                reconnect_time_wait=2,
                max_reconnect_attempts=60,
                error_cb=self._on_error,
                disconnected_cb=self._on_disconnected,
                reconnected_cb=self._on_reconnected,
            )
            self._js = self._nc.jetstream()
            await self._bootstrap_streams()
            logger.info("Connected to NATS: %s", self._url)

    async def _bootstrap_streams(self) -> None:
        assert self._js is not None
        for cfg in STREAMS:
            try:
                await self._js.stream_info(cfg.name)
            except nats.js.errors.NotFoundError:
                await self._js.add_stream(
                    name=cfg.name,
                    subjects=cfg.subjects,
                    max_age=cfg.max_age_seconds,
                    max_bytes=cfg.max_bytes,
                    storage=cfg.storage,
                    retention=cfg.retention,
                )
                logger.info("Created stream: %s", cfg.name)

    async def close(self) -> None:
        if self._nc is not None and not self._nc.is_closed:
            await self._nc.drain()
            self._nc = None
            self._js = None

    @property
    def js(self) -> JetStreamContext:
        if self._js is None:
            raise RuntimeError("NATS not connected. Call connect() first.")
        return self._js

    async def _on_error(self, e: Exception) -> None:
        logger.error("NATS error: %s", e)

    async def _on_disconnected(self) -> None:
        logger.warning("NATS disconnected")

    async def _on_reconnected(self) -> None:
        logger.info("NATS reconnected")


@asynccontextmanager
async def nats_connection(url: str, *, name: str) -> AsyncIterator[NATSConnection]:
    conn = NATSConnection(url, name=name)
    await conn.connect()
    try:
        yield conn
    finally:
        await conn.close()
```

### `publisher.py`

```python
from uuid import UUID
from typing import Any

from contracts.base import EventEnvelope
from contracts.events import EVENT_PAYLOAD_MAP
from nats_client.client import NATSConnection
from nats_client.subjects import Subjects


class Publisher:
    """Публикует события в NATS JetStream."""

    def __init__(self, conn: NATSConnection, *, producer: str) -> None:
        self._conn = conn
        self._producer = producer

    async def publish(
        self,
        subject: Subjects,
        tenant_id: UUID,
        payload: dict[str, Any],
        *,
        trace_id: str = "",
        correlation_id: UUID | None = None,
        causation_id: UUID | None = None,
    ) -> None:
        event_type = subject.value
        if event_type not in EVENT_PAYLOAD_MAP:
            raise ValueError(f"Unknown event type: {event_type}")

        payload_cls = EVENT_PAYLOAD_MAP[event_type]
        envelope = EventEnvelope[payload_cls](  # type: ignore[valid-type]
            event_type=event_type,
            occurred_at=__import__("datetime").datetime.now(__import__("datetime").timezone.utc),
            tenant_id=tenant_id,
            trace_id=trace_id,
            causation_id=causation_id,
            correlation_id=correlation_id,
            producer=self._producer,
            payload=payload_cls.model_validate(payload),
        )

        full_subject = Subjects.full(subject, str(tenant_id))
        await self._conn.js.publish(
            full_subject,
            envelope.model_dump_json().encode(),
            headers={
                "Nats-Msg-Id": str(envelope.event_id),
                "X-Trace-Id": trace_id,
                "X-Tenant-Id": str(tenant_id),
                "X-Schema-Version": envelope.schema_version,
            },
        )
```

**Важно:** `Nats-Msg-Id` — для дедупликации на стороне NATS. Если publish с тем же msg-id — NATS отбросит дубликат (в пределах окна дедупликации).

### `subscriber.py`

```python
import logging
from collections.abc import Awaitable, Callable
from typing import Any

import nats
from nats.js.api import ConsumerConfig, DeliverPolicy

from contracts.base import EventEnvelope
from contracts.events import EVENT_PAYLOAD_MAP, parse_event
from nats_client.client import NATSConnection
from nats_client.streams import STREAMS


logger = logging.getLogger(__name__)


Handler = Callable[[EventEnvelope], Awaitable[None]]


class Subscriber:
    """Pull-consumer для обработки событий."""

    def __init__(
        self,
        conn: NATSConnection,
        *,
        stream: str,
        durable: str,
        filter_subjects: list[str],
        handler: Handler,
    ) -> None:
        self._conn = conn
        self._stream = stream
        self._durable = durable
        self._filter = filter_subjects
        self._handler = handler
        self._sub = None

    async def start(self) -> None:
        assert self._conn.js is not None
        config = ConsumerConfig(
            durable_name=self._durable,
            filter_subjects=self._filter,
            deliver_policy=DeliverPolicy.ALL,
            ack_wait=30,
            max_deliver=5,
        )
        self._sub = await self._conn.js.pull_subscribe(
            subject=self._filter[0] if len(self._filter) == 1 else ">",
            durable=self._durable,
            stream=self._stream,
            config=config,
        )
        logger.info("Subscribed: stream=%s durable=%s", self._stream, self._durable)

    async def run_forever(self) -> None:
        assert self._sub is not None
        while True:
            try:
                messages = await self._sub.fetch(batch=10, timeout=5)
            except nats.errors.TimeoutError:
                continue
            for msg in messages:
                await self._process(msg)

    async def _process(self, msg) -> None:
        try:
            envelope = parse_event(
                event_type=msg.headers.get("X-Event-Type", ""),
                data=__import__("json").loads(msg.data),
            )
        except Exception as e:
            logger.exception("Failed to parse event: %s", e)
            await msg.term()
            return

        try:
            await self._handler(envelope)
            await msg.ack()
        except Exception as e:
            logger.exception("Handler failed: %s", e)
            await msg.nak(delay=5)
```

```python
class TenantMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next) -> Response:

            return await call_next(request)

        raw = request.headers.get("X-Tenant-ID")
```

### `middleware/idempotency.py`

```python
import hashlib
import json

from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from starlette.responses import JSONResponse, Response

from common.redis import get_redis


IDEMPOTENT_METHODS = {"POST", "PUT", "PATCH"}


class IdempotencyMiddleware(BaseHTTPMiddleware):
    """Требует Idempotency-Key на мутирующих запросах.

    Если ключ уже использован — возвращает сохранённый ответ.
    """

    def __init__(self, app, *, ttl_seconds: int = 86400) -> None:
        super().__init__(app)
        self._ttl = ttl_seconds

    async def dispatch(self, request: Request, call_next) -> Response:
        if request.method not in IDEMPOTENT_METHODS:
            return await call_next(request)

        # Некоторые пути могут быть исключены
        if request.url.path in {"/healthz", "/readyz"}:
            return await call_next(request)

        key = request.headers.get("Idempotency-Key")
        if not key:
            return await call_next(request)  # ключ опционален

        redis = get_redis()
        tenant_id = request.headers.get("X-Tenant-ID", "no-tenant")
        cache_key = f"idem:{tenant_id}:{key}"

        cached = await redis.get(cache_key)
        if cached is not None:
            data = json.loads(cached)
            return JSONResponse(
                content=data["body"],
                status_code=data["status"],
                headers={"X-Idempotent-Replay": "true"},
            )

        # Обрабатываем
        response = await call_next(request)

        # Читаем body — нужно пересобрать response. В Starlette это нетривиально.
        # Упрощение: сохраняем только статус и headers, body для стриминговых не сохраняем.
        # Для MVP: собираем body через обёртку.
        body_bytes = b""
        async for chunk in response.body_iterator:  # type: ignore[attr-defined]
            body_bytes += chunk

        try:
            body_json = json.loads(body_bytes) if body_bytes else None
        except json.JSONDecodeError:
            body_json = None

        if 200 <= response.status_code < 300 and body_json is not None:
            await redis.setex(
                cache_key,
                self._ttl,
                json.dumps({"status": response.status_code, "body": body_json}),
            )

        return Response(
            content=body_bytes,
            status_code=response.status_code,
            headers=dict(response.headers),
            media_type=response.media_type,
        )
```

**Важно:** этот middleware пересобирает response. На проде лучше использовать `starlette-context` или специализированную либу. Для MVP — ок.

```python
from sqlalchemy.ext.asyncio import AsyncSession

from tenant_service.models import Tenant


class TenantRepository:
    def __init__(self, session: AsyncSession) -> None:
        self._s = session

    async def get(self, tenant_id: UUID) -> Tenant | None:
        return await self._s.get(Tenant, tenant_id)

    async def get_by_slug(self, slug: str) -> Tenant | None:
        stmt = select(Tenant).where(Tenant.slug == slug)
        return (await self._s.execute(stmt)).scalar_one_or_none()

    async def list(
        self, *, status: str | None = None, include_archived: bool = False
    ) -> list[Tenant]:
        stmt = select(Tenant)
        if status is not None:
            stmt = stmt.where(Tenant.status == status)
        elif not include_archived:
            stmt = stmt.where(Tenant.status != "archived")
        stmt = stmt.order_by(Tenant.created_at.desc())
        return list((await self._s.execute(stmt)).scalars().all())

    async def add(self, tenant: Tenant) -> Tenant:
        self._s.add(tenant)
        await self._s.flush()
        return tenant
```

```python
import structlog
from uuid import UUID

from common.errors import ConflictError, NotFoundError
from tenant_service.models import Tenant
from tenant_service.repository import TenantRepository
from tenant_service.schemas import TenantCreate, TenantUpdate


logger = structlog.get_logger()


class TenantService:
    def __init__(self, repo: TenantRepository) -> None:
        self._repo = repo

    async def create(self, data: TenantCreate, *, created_by: str = "system") -> Tenant:
        existing = await self._repo.get_by_slug(data.slug)
        if existing is not None:
            raise ConflictError(f"Tenant with slug '{data.slug}' already exists")

        tenant = Tenant(
            name=data.name,
            slug=data.slug,
            status="active",
            is_sandbox=data.is_sandbox,
            created_by=created_by,
        )
        return await self._repo.add(tenant)

    async def get(self, tenant_id: UUID) -> Tenant:
        tenant = await self._repo.get(tenant_id)
        if tenant is None:
            raise NotFoundError(f"Tenant {tenant_id} not found")
        return tenant

    async def update(self, tenant_id: UUID, data: TenantUpdate) -> Tenant:
        tenant = await self.get(tenant_id)
        if data.name is not None:
            tenant.name = data.name
        if data.status is not None:
            tenant.status = data.status
        await self._repo._s.flush()
        return tenant

    async def archive(self, tenant_id: UUID) -> Tenant:
        tenant = await self.get(tenant_id)
        tenant.status = "archived"
        await self._repo._s.flush()
        return tenant

    async def restore(self, tenant_id: UUID) -> Tenant:
        tenant = await self.get(tenant_id)
        tenant.status = "active"
        await self._repo._s.flush()
        return tenant
```

**Важно:** для `POST /tenants` (создание нового) RLS-политика `USING (id = ...)` не сработает — `current_setting` вернёт NULL. Нужно либо:

- (B) Использовать отдельную роль для INSERT.
- (C) Разрешить `current_setting` = NULL для INSERT.

Правильное решение (A):

```sql
CREATE POLICY tenants_self_isolation ON tenants
  USING (id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (true);
```

`USING` — для SELECT/UPDATE/DELETE (фильтр). `WITH CHECK` — для INSERT/UPDATE (валидация). `WITH CHECK (true)` разрешает INSERT любого тенанта, что логично: тенант создаётся до того, как он сам себе установлен.

- **`get_service` через `yield`** — FastAPI автоматически закрывает сессию.

```python
import time
import httpx

from llm_gateway.providers.base import LLMProvider, LLMRequest, LLMResponse


# Цены DeepSeek на момент написания (уточнять в актуальной документации)
PRICES = {
    "deepseek-chat": {"in": 0.14 / 1_000_000, "out": 0.28 / 1_000_000},
    "deepseek-reasoner": {"in": 0.55 / 1_000_000, "out": 2.19 / 1_000_000},
}


class DeepSeekProvider(LLMProvider):
    name = "deepseek"

    def __init__(self, api_key: str, base_url: str) -> None:
        self._client = httpx.AsyncClient(
            base_url=base_url,
            headers={"Authorization": f"Bearer {api_key}"},
            timeout=httpx.Timeout(120.0, connect=10.0),
        )

    async def complete(self, req: LLMRequest) -> LLMResponse:
        messages = []
        if req.system:
            messages.append({"role": "system", "content": req.system})
        messages.append({"role": "user", "content": req.user})

        payload = {
            "model": req.model,
            "messages": messages,
            "temperature": req.temperature,
            "max_tokens": req.max_tokens,
        }
        if req.json_mode:
            payload["response_format"] = {"type": "json_object"}

        started = time.monotonic()
        response = await self._client.post("/v1/chat/completions", json=payload)
        response.raise_for_status()
        latency_ms = int((time.monotonic() - started) * 1000)

        data = response.json()
        text = data["choices"][0]["message"]["content"]
        usage = data["usage"]
        tokens_in = usage["prompt_tokens"]
        tokens_out = usage["completion_tokens"]

        prices = PRICES.get(req.model, PRICES["deepseek-chat"])
        cost = tokens_in * prices["in"] + tokens_out * prices["out"]

        return LLMResponse(
            text=text,
            model=data["model"],
            tokens_in=tokens_in,
            tokens_out=tokens_out,
            cost_usd=cost,
            latency_ms=latency_ms,
            raw=data,
        )

    async def close(self) -> None:
        await self._client.aclose()
```

```python
import hashlib
import json

from redis.asyncio import Redis

from llm_gateway.schemas import CompleteRequest


def prompt_hash(req: CompleteRequest) -> str:
    payload = {
        "system": req.system,
        "user": req.user,
        "model": req.model,
        "temperature": req.temperature,
        "max_tokens": req.max_tokens,
        "json_mode": req.json_mode,
    }
    blob = json.dumps(payload, sort_keys=True, ensure_ascii=False).encode()
    return hashlib.sha256(blob).hexdigest()


async def cache_get(redis: Redis, key: str) -> dict | None:
    raw = await redis.get(f"llm:cache:{key}")
    if raw is None:
        return None
    return json.loads(raw)


async def cache_set(redis: Redis, key: str, value: dict, *, ttl: int = 86400) -> None:
    await redis.setex(f"llm:cache:{key}", ttl, json.dumps(value, ensure_ascii=False))
```

```python
import structlog
from uuid import UUID

from common.context import get_trace_id, get_tenant_id
from common.errors import AppError
from llm_gateway.cache import cache_get, cache_set, prompt_hash
from llm_gateway.langfuse_client import LangfuseClient
from llm_gateway.models import LLMCall
from llm_gateway.providers.registry import ProviderRegistry
from llm_gateway.schemas import CompleteRequest, CompleteResponse


logger = structlog.get_logger()


class LLMGatewayService:
    def __init__(
        self,
        registry: ProviderRegistry,
        session,
        redis,
        langfuse: LangfuseClient | None,
    ) -> None:
        self._registry = registry
        self._session = session
        self._redis = redis
        self._langfuse = langfuse

    async def complete(self, req: CompleteRequest) -> CompleteResponse:
        tenant_id = get_tenant_id()
        if tenant_id is None:
            raise AppError("X-Tenant-ID required", code="missing_tenant", status_code=400)

        trace_id = get_trace_id() or ""
        ph = prompt_hash(req)

        if req.use_cache:
            cached = await cache_get(self._redis, ph)
            if cached is not None:
                logger.info("llm_cache_hit", task=req.task_type, prompt_hash=ph)
                return CompleteResponse(**cached, cached=True)

        provider = self._registry.default()
        try:
            result = await provider.complete(
                __import__("llm_gateway.providers.base", fromlist=["LLMRequest"]).LLMRequest(
                    system=req.system,
                    user=req.user,
                    model=req.model,
                    temperature=req.temperature,
                    max_tokens=req.max_tokens,
                    json_mode=req.json_mode,
                )
            )
        except Exception as e:
            logger.exception("llm_provider_failed", task=req.task_type)
            await self._record_error(tenant_id, req, ph, str(e), trace_id)
            raise AppError(f"LLM provider failed: {e}", code="llm_error", status_code=502)

        response = CompleteResponse(
            text=result.text,
            model=result.model,
            tokens_in=result.tokens_in,
            tokens_out=result.tokens_out,
            cost_usd=result.cost_usd,
            latency_ms=result.latency_ms,
        )

        await self._record_success(tenant_id, req, ph, result, trace_id)

        if req.use_cache:
            await cache_set(self._redis, ph, response.model_dump())

        if self._langfuse is not None:
            self._langfuse.trace(
                name=req.task_type,
                tenant_id=str(tenant_id),
                trace_id=trace_id,
                input_data={"system": req.system, "user": req.user},
                output_data={"text": result.text},
                model=result.model,
                tokens_in=result.tokens_in,
                tokens_out=result.tokens_out,
                cost_usd=result.cost_usd,
                latency_ms=result.latency_ms,
            )

        return response

    async def _record_success(self, tenant_id, req, ph, result, trace_id) -> None:
        call = LLMCall(
            tenant_id=tenant_id,
            task_type=req.task_type,
            provider="deepseek",
            model=result.model,
            prompt_hash=ph,
            tokens_in=result.tokens_in,
            tokens_out=result.tokens_out,
            cost_usd=result.cost_usd,
            latency_ms=result.latency_ms,
            request_body={"system": req.system, "user": req.user, "model": req.model},
            response_text=result.text,
            langfuse_trace_id=trace_id or None,
        )
        self._session.add(call)

    async def _record_error(self, tenant_id, req, ph, error, trace_id) -> None:
        call = LLMCall(
            tenant_id=tenant_id,
            task_type=req.task_type,
            provider="deepseek",
            model=req.model,
            prompt_hash=ph,
            tokens_in=0,
            tokens_out=0,
            cost_usd=0,
            latency_ms=0,
            request_body={"system": req.system, "user": req.user, "model": req.model},
            response_text="",
            error=error,
            langfuse_trace_id=trace_id or None,
        )
        self._session.add(call)
```

- **DeepSeek API:** OpenAI-совместимый. Base URL `https://api.deepseek.com`. Модели: `deepseek-chat`, `deepseek-reasoner`.
- **Langfuse SDK:** `pip install langfuse`. `Langfuse(public_key=..., secret_key=..., host=...)`. `flush()` вызывается периодически или вручную.
- **Кэш:** ключ — sha256 от нормализованного запроса. TTL 24 часа.
- **`use_cache: false`** — для случаев, когда нужна свежая генерация (например, при A/B).

- ❌ Не делать `use_cache: true` для творческих задач (генерация писем).
